# AGENTS.md

lintoko is a Rust CLI that lints Motoko source using tree-sitter queries defined in TOML rule files.

## Where lintoko fits

lintoko sees syntax only: it never type-checks, and leaves anything the compiler (`moc`) rejects to the compiler. Most users run it through mops rather than directly.

- [`tree-sitter-motoko`](https://github.com/caffeinelabs/tree-sitter-motoko) — the grammar lintoko parses with. Every node name a rule matches (`let_else_dec`, `bin_exp_*`, ...) comes from its `src/node-types.json`; syntax changes land there first and reach lintoko through a `rev` bump (see below). `just play` in that repo opens the tree-sitter playground, the quickest way to see the tree a query has to match.
- `mo-fmt` — the Motoko formatter, in the `mo-fmt/` directory of tree-sitter-motoko and built on the same grammar. lintoko only lints; formatting is mo-fmt's job (or prettier-plugin-motoko's, which `mops format` uses unless `mo-fmt` is pinned).
- [mops](https://github.com/caffeinelabs/mops) — the Motoko package manager, and the usual way lintoko runs ([`mops lint` docs](https://docs.mops.one/cli/mops-lint)):
  - `[toolchain] lintoko` in `mops.toml` takes a version, which mops downloads from this repo's GitHub releases, or a file path. Point it at `target/debug/lintoko` to try a local build in a real project.
  - `mops lint` runs lintoko from the project root with one `--rules` flag per rule directory: `lint/` or `lints/` (or `[lint] rules`), plus the `rules/` directory of each dependency named in `[lint] extends` (all of them with `extends = true`). `[lint.extra]` runs lintoko again with more rule directories on files matching a glob.
  - `mops lint` passes files as absolute paths. Before matching `includes`/`excludes` globs, lintoko strips its working directory (the project root) from absolute paths, so a pattern like `backend/types/**` matches the same under `mops lint` as when lintoko is run by hand on `backend/types/foo.mo`. Diagnostics still print the path as passed.
  - `mops check` runs the lint step after type-checking whenever lintoko is pinned.

## Build, test, lint, format

The `justfile` defines the common tasks (requires the [`just`](https://just.systems/) runner):

- `just build` — `cargo build`
- `just build-release` — `cargo build --release`
- `just test` — `cargo test`
- `just test-accept` — accept insta snapshot changes (`INSTA_UPDATE=always cargo test`)
- `just fmt` — `cargo fmt --all`
- `just lint` — `cargo clippy --all-targets -- -D warnings` then `cargo fmt --all --check`
- `just install` — `cargo install --path .`
- `just run FILES...` — lints with rules from `custom-rules/`, a local directory that is not checked in
- `just` (default) — runs `lint` then `test`

These also work directly with `cargo` if `just` is unavailable. To iterate on one rule, pass the rule file instead of a directory: `cargo run -- -r my-rule.toml sample.mo` runs only that rule.

## CI

`.github/workflows/ci.yml` runs `cargo build`, `cargo test`, clippy with `-D warnings`, and `cargo fmt --all --check` on pushes and PRs to `main`, the same checks as `just`. Run `just` before pushing.

`.github/workflows/release.yml` is generated by cargo-dist. Don't edit it by hand: change `dist-workspace.toml` and run `dist generate`, which refuses to run unless your installed dist matches the `cargo-dist-version` pinned there.

## Layout

- `src/lib.rs` — rule loading, query matching, diagnostics and `--fix`; `src/main.rs` — CLI and input expansion.
- `src/custom_predicates.rs` — the `@trailing` and `@filter` captures and lintoko's own predicates, `#ancestor-depth?` and `#subtree-depth?` (see `example-rules/nesting-limit.toml`).
- `src/snapshots/` — insta snapshots; regenerate with `just test-accept`, never hand-edit.
- `example-rules/` — example TOML rules, and test input. The snapshot tests run all of them against `test-data.mo` (linted as `backend/main.mo`), and unit tests in `lib.rs` load some by file name, so renaming or changing a rule breaks tests.
- `.agents/skills/lintoko/SKILL.md` — the rule-authoring reference (TOML fields, special captures, query patterns, pitfalls), shipped as an agent skill. Read it before writing or reviewing rules, and update it in the same PR when the rule format, captures, predicates or CLI flags change.

## Bumping the grammar

- `tree-sitter-motoko` is a git dependency pinned to a `rev` in `Cargo.toml`. Prefer the commit of a grammar release tag and name the tag in the CHANGELOG, as 0.12.0 does.
- After a bump, run `cargo build` to update `Cargo.lock`, then `just test` and review the snapshot diff before `just test-accept`. A query naming a removed node type fails as soon as the rule runs on a file, but a changed tree shape just stops matching, so look for diagnostics that disappeared.
- Grammar changes that break existing rules go in the CHANGELOG as `breaking (custom rules):` with the old and new node shapes, since users' own rule directories break too.

## Conventions and gotchas

- Rust edition is 2024 and the code uses let-chains, so it needs Rust 1.88 or newer. No toolchain file pins it; CI uses the runner's stable Rust.
- Error diagnostics make lintoko exit non-zero; warnings are printed but exit 0. `mops lint` and `mops check` rely on that exit code.
- Diagnostics and the final summary go to stderr; stdout stays empty.
- Snapshot tests set `NO_COLOR=1`; keep output deterministic.
- `deny.toml` restricts allowed dependency licenses. CI does not run cargo-deny, so check new dependencies with `cargo deny check licenses`.

## Changelog and releases

- Add user-facing changes to `CHANGELOG.md` under a `# Unreleased` header at the top (create it if the last release removed it), one `- feat:` / `- fix:` / `- chore:` / `- breaking:` bullet each. PR titles mostly use the same prefixes.
- Releases are automated by cargo-dist (config in `dist-workspace.toml`); see `DEVELOPMENT.md` for the flow: rename the `Unreleased` header, bump the version in `Cargo.toml` and run `cargo build` to update `Cargo.lock`, merge a `release: X.Y.Z` PR, then push the `vX.Y.Z` tag.
- Release asset names are an interface: mops downloads `lintoko-<arch>-<apple-darwin|unknown-linux-gnu>.tar.xz`. Renaming archives or dropping one of the `targets` in `dist-workspace.toml` breaks `mops toolchain` installs on that platform.
